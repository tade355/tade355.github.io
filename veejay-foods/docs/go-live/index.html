From today’s working build to a live, public app: every step, the accounts and tools you need, who does what, and what can and can’t be done for you.

Companion files: Design & delivery plan · Architecture notes · repository README

1 · Where we are today

The app is a working, tested build with sample data. It is not yet running on the internet, and it has never handled a real payment. The distance to launch is mostly accounts, approvals, real content and real-device testing — not new features.

Done and verified

  • Customer app, API and staff/admin dashboard are built (all nine planned capabilities).
  • 67 automated backend tests pass on a real PostgreSQL database — payments webhook, order states, QR pickup, sessions, refunds, slots.
  • App type-checks and bundles for Android; dashboard builds; full customer and staff flows were driven in a browser against the live API.
  • Production start-up verified: npm run build then npm start serves the API; .env files load; an initial database migration applies cleanly to an empty database with zero drift.
  • A production-safe command to create the first admin (admin:create) — separate from the sample-data seed.
  • Brand applied (name, logo, colours); launch area set to Abuja.

Not done yet

  • No hosting, domain or live database.
  • No Paystack live account; real payments, refunds, SMS and push notifications have never been exercised (tests use stand-ins).
  • Never run on a physical iPhone or Android phone.
  • Outlets, menu, prices and photos are samples (Wuse II, Garki, Jabi).
  • Photos are stored on the server’s disk (lost on redeploy).
  • No in-app account deletion, privacy policy or terms (both app stores require them).
  • No store accounts, store listings, or mobile build configuration.
  • No monitoring, alerting or restore-tested backups.

Bottom line

Yes, the app can be deployed, launched, handed over and opened to the public. Expect roughly 4–8 weeks from the day accounts are opened. The hands-on work is about 2–3 weeks; the rest is waiting for Paystack, SMS sender-ID and app-store approvals, which you do not control. (These are estimates, not guarantees.)

How to read this guide

Every step carries an owner tag:

YOU the developer/agency delivering the project   CLIENT Veejay Foods (owner/admin; legal and payment identity)   CLAUDE work I can do in this repository   TOGETHER needs both

Each phase ends with a “Done when” test. Don’t start the next phase until it passes — most launch problems come from skipping one.

The critical path is approvals, not code

Start Phase 1 on day one and in this order: (1) Paystack business verification, (2) SMS sender-ID registration, (3) Apple and Google developer accounts. Each can take days to weeks and none can be rushed from our side. Everything else can run while you wait. If any of these stalls, the launch date moves — nothing else will.

3 · What I can do, what I can’t, and what only you or the client can do

I’m Claude, working inside this code repository. This is the honest boundary, so nobody plans around something that can’t happen.

✔ I can do

  • Write and change code in the app, API and dashboard; add tests; run builds and the test suite here.
  • Create deployment files: Docker/host configuration, eas.json, CI workflows, environment templates.
  • Add the missing production features: account deletion, cloud image storage, restricted CORS, reviewer test login, error monitoring.
  • Write runbooks, checklists, staff quick-cards, store-listing text, and a draft privacy policy and terms.
  • Prepare menu/outlet import from a spreadsheet you supply.
  • Generate screenshots for store listings from the web build.
  • Walk you through each console click-by-click and read logs or error messages you paste.
  • Re-run the whole test suite and re-generate this document as things change.

✘ I can’t do

  • Create or verify accounts (Paystack, Apple, Google, SMS, hosting). They need identity, bank details, documents and payment cards.
  • Log in to the client’s accounts, or hold their secrets. (Don’t paste keys into chat.)
  • Deploy to a host from this sandbox — I have no credentials and limited outbound access. I can prepare everything; a person runs the deploy.
  • Run the app on a physical iPhone/Android, test real SMS delivery, real push, or a real card or bank transfer.
  • Submit to the App Store / Play Store or talk to reviewers; I can write the answers.
  • Speed up or guarantee any third-party approval.
  • Give legal advice (privacy law, tax, contracts) — drafts need a lawyer’s review.
  • Supply the real menu, prices, photos or addresses.
  • Monitor the live system after this conversation ends, or be on call.
  • Make business decisions (refund policy, opening hours, pricing).

★ Only you / the client can

  • CLIENT Legal identity: business registration documents, signing agreements, bank settlement account.
  • CLIENT Real content: outlets, menu, prices, photos, support contact.
  • CLIENT Business rules: refunds, order cut-offs, who is staff/admin.
  • CLIENT Paying for accounts, SMS credit and hosting.
  • YOU Run deployments, builds and submissions with the client’s credentials.
  • YOU Hold the phones for device testing (one Android, one iPhone minimum).
  • TOGETHER Train staff; run the soft launch; sign off acceptance.

Practical working rule

Keep all secrets in a password manager owned by the client and typed straight into the host’s settings page. When I need to know whether something is set up correctly, share the names of the settings and the error text — never the values.

Proposed go / no-go checks before the public launch

Targets to agree with the client — these are suggestions, not measured facts.

  • Zero lost payments: every successful Paystack charge has a matching order or refund
  • Login codes arrive within an agreed time on all four networks
  • No unresolved crash reports; no must-fix bugs
  • Refunds work end to end, and staff are confident handing over by QR
  • Feedback from invitees reviewed; top issues fixed

PHASE 8

Handover & hypercare

Owner: TOGETHER · 2 weeks of close support after launch, then a maintenance arrangement

Ownership transfer checklist

  • Client is the Owner / Account Holder on: GitHub, Paystack, SMS provider, Apple, Google Play, Expo, hosting, database, domain/DNS, storage, monitoring
  • Developer access reduced to “team member” (or removed) on each — and production secrets rotated so the developer no longer holds working copies
  • Password-manager vault contents verified by the client (every login and key present and working)
  • Store accounts: client’s email for notices; two-factor on for every account; a second admin added in case the owner is unavailable
  • Renewal calendar created: Apple yearly fee, domain, certificates, SMS credit top-ups, hosting plan
  • Final backup restore test performed with the client watching

What the client receives

  • Runbook — “if X happens, do Y” (see section 7).
  • Staff quick-card and a short admin guide: menu, outlets, staff, refunds, reports.
  • This guide, the design & delivery plan, and the architecture notes.
  • Repository README — how to run, test, build and deploy.
  • Environment-settings sheet — every setting name, what it does, where it lives (values stay in the vault).

If something goes wrong

SymptomFirst checks
Customer paid but sees no order1) Find the charge in the Paystack dashboard. 2) Check the webhook log there and resend it if it failed. 3) Ask the customer to open the order (the app re-checks with Paystack automatically). 4) If the pickup slot had expired, the system refunds automatically — confirm the refund in Paystack.
Login code doesn’t arriveSMS wallet balance and delivery report; try another network; confirm the sender ID is still approved; wait a minute before requesting again (the system limits repeat requests).
Staff can’t scanDashboard must be on HTTPS; allow camera permission in the browser; use the order-code fallback so the customer isn’t held up.
Refund stuck “pending”Check the refund in Paystack; they confirm asynchronously. If it shows processed there but not in the dashboard, check the webhook log.
App or API downThe uptime monitor should alert first. Check the host’s status page and logs; the database host’s status; recent deployments (roll back the last one if it started right after a release).
Wrong price or sold-out itemMenu tab: edit the price, or toggle that outlet’s availability. Existing orders keep the price they were placed at.
A staff member leavesStaff tab → remove access; takes effect immediately.

Appendix D · Plain-English glossary

APIThe server the app and dashboard talk to; it holds the rules and the database.
WebhookPaystack calling our server to say “this payment succeeded”. Verified with a secret signature.
OTPOne-time password — the 6-digit login code sent by SMS.
MigrationA versioned change to the database structure, applied the same way in every environment.
StagingA private rehearsal copy of the whole system, using test money.
EAS / ExpoThe cloud service that builds the iPhone and Android apps and sends them to the stores.
TestFlight / internal testingApple’s and Google’s official ways to give a test build to a few people before the public release.
Staged rolloutReleasing to a small percentage of users first, then widening if all is well.
DNDDo-Not-Disturb registry; some SMS routes don’t deliver to numbers on it.
NDPANigeria Data Protection Act — rules for handling personal data such as phone numbers and photos.
